# Contributing to Wisp

Thanks for helping. Bug reports, fixes and small focused features are all
welcome. For anything large, open an issue first so we can agree on the shape
before you write it. By taking part you agree to the
[Code of Conduct](CODE_OF_CONDUCT.md).

Security problems go through
[private vulnerability reporting](SECURITY.md), not public issues.

## Build and run

You need [Rust](https://rustup.rs) (stable). On Windows you also need the
WebView2 runtime, which Windows 11 already has.

```bash
cargo run
```

## Before you open a pull request

`main` is protected: changes arrive by pull request, and CI runs these on macOS
and Windows. Run them yourself first:

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

If you work on macOS, also check that the Windows code still compiles
(`rustup target add x86_64-pc-windows-msvc` once):

```bash
cargo clippy --target x86_64-pc-windows-msvc -- -D warnings
```

Then:

- Add a line under **Unreleased** in [CHANGELOG.md](CHANGELOG.md) for anything
  a user would notice.
- If the app starts sending anything new over the network, say so in
  [PRIVACY.md](PRIVACY.md). That document is a promise.

## Interface changes

The interface lives in `src/ui.html` and follows
[docs/DESIGN.md](docs/DESIGN.md): design tokens only (no one-off colors, sizes
or durations), line icons, no emoji.

A debug build on macOS can save a picture of its own window, which is the
easiest way to show a change in a pull request:

```bash
HOME=/tmp/wisp-home WISP_ACT=settings WISP_SHOT=/tmp/wisp.png target/debug/wisp
```

`WISP_ACT` runs an action first (here: open Settings), the throwaway `HOME`
keeps your own profile out of it, and the app quits after six seconds.

## Dependencies and license notices

Wisp ships the license text of every crate it is built from in
[THIRD-PARTY-NOTICES](THIRD-PARTY-NOTICES), generated by
[cargo-about](https://github.com/EmbarkStudios/cargo-about). After adding,
removing or updating a dependency, regenerate it and commit the result:

```bash
cargo install cargo-about --locked --version 0.9.3 --features cli
cargo about generate --locked --fail about.hbs -o THIRD-PARTY-NOTICES
```

CI fails when the file is out of date. The command fails when a crate uses a
license that is not in the `accepted` list in `about.toml`; add a license there
only after checking that it is compatible with shipping Wisp under MIT.

## Releases

A release is published when the version in `Cargo.toml` changes on `main`.
Maintainers: move the **Unreleased** entries in `CHANGELOG.md` under the new
version, bump `version` in `Cargo.toml`, and merge that pull request. The
Release workflow sees a version with no tag, builds the installers, signs the
update files, and publishes the release (which creates the tag). Ordinary merges
publish nothing. Installed copies then update themselves.

To build an installer by hand:

```bash
cargo install cargo-packager --locked
cargo build --release
cargo packager --release --formats dmg   # or: --formats nsis on Windows
```

### Update signing key (one-time setup)

Automatic updates need a signing key pair. Generate it once and keep the
private half safe: anyone holding it can ship an update to every installed copy,
and if it is lost, installed copies can no longer be updated automatically.

```bash
cargo packager signer generate --path ~/.wisp/update.key
```

Then, in the repository's settings on GitHub (Secrets and variables > Actions):

- secret `WISP_UPDATE_PRIVATE_KEY`: the contents of `~/.wisp/update.key`
- secret `WISP_UPDATE_PRIVATE_KEY_PASSWORD`: the password you chose
- variable `WISP_UPDATE_PUBKEY`: the contents of `~/.wisp/update.key.pub`

From the next release on, the workflow signs the update files and publishes
`latest.json`, which installed copies read. Without the key, releases are built
as before and offer no automatic update. Copies you build yourself do not
update.

The banner, wordmark, download buttons and screenshots used by the README are
